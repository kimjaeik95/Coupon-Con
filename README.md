## 1. 프로젝트 개요
### 1-1. 프로젝트 소개
- 대규모 트래픽 상황에서 쿠폰 중복 발급 및 재고 초과 발급 문제를 방지하기 위해 동시성 제어가 적용된 선착순 쿠폰 이벤트 시스템을 개발하였습니다.
### 1-2. 문제 정의
-  사용자가 동시에 쿠폰을 요청할 경우, 재고보다 많은 수량이 발급되는 "중복 발급 및 초과 발급 이슈가"가 발생 할 수 있습니다.
-  단일 서버 환경뿐 아니라 멀티 서버 환경에서도 데이터 정합성 보장이 어려운 문제가 존재합니다.
-  동기식 문제점 : 락을 잡은 트랜잭션 안에 멤버조회 + 쿠폰조회 + 쿠폰 수량 update + 쿠폰 발급 insert가 하나의 트랜잭션으로 연결되어 여러 트래픽이 들어오면 락을 대기하는 시간에 Tomcat 스레드가 계속 점유되어 스레드풀이 고갈되고, HTTP 연결도 계속 유지되며, DB Connection도 트랜잭션이 끝날때까지 점유됩니다.
그 결과 락 유지 시간이 길어졌고 다른 요청들이 Lock을 대기하면서 TPS가 감소하고 대기 중인 요청들이 DB 커넥션을 점유하여 커넥션 풀이 부족해지고 MySQL CPU 사용률이 늘어나  병목현상을 확인했습니다
### RabbitMQ 도입 이유
쿠폰 발급이벤트는 유실없이 순차적으로 처리해야 하며 쿠폰재고의 정합성을 지켜 처리해야하는 서비스로 Kafka만큼의 운영 부담이 없고 메시지 유실이 없는 비동기 작업큐인 RabbitMQ가 적합하다고 생각해 선정했습니다.
기존 동기 방식의 문제
### 1-3. 문제 해결 전략
- **단계별 락 적용**을 통해 쿠폰 수량에 대한 정합성을 확보합니다.
  - 1단계: 단일 인스턴스 환경에서 **JVM `synchronized`** 사용 
  - 2단계: DB차원에서 **낙관적 락(Optimistic Lock)**, **비관적 락(Pessimistic Lock)** 사용
  - 3단계:  **Redis 분산락(Redisson)** Lettuce SpinLock, Redisson Lock을 도입하여 멀티 인스턴스 환경에서도 동시성 문제 해결
### 1-4. 기술 스택
- **Language: Java**
- **Server: 로컬 환경 (localhost:8080, 8081에서 테스트 진행)**
- **DB: Mysql**
- **Tech: Spring Boot, Mybatis , Redis , RabbitMQ, SSE, Docker , Flyway , Grafana/Prometheus**

### 3. 향후 및 개선점
트래픽이 늘어나게 된다면  발행(Publish) 속도가 소비(Consume) 처리속도가 따라가지못해
병목부분이 될것입니다.  
병목이 되는 이유는  Consume 로직 내  Redis Lock 여전히 발생하며  락의 인한 대기가 이뤄지고있어 처리속도가 1:1로 따라가지 못한다는 점입니다.  
이부분을 해결하기 위해서는 DB에서 쿠폰차감을 하는게아닌  Redis에서 재고를 차감해야합니다.


Redis Lua Script 방식이 있습니다. 

장점

- DB를 거의 안 건드린다.
- Redis가 메모리라 매우 빠르다.
- 초당 수만~수십만 요청도 가능하다.

단점
- Redis와 DB의 데이터 동기화가 필요하다.
- 구현이 더 복잡하다.


Redis로 원자적 재고를 차감하게 된다면 락이 필요하지않아 처리량을 높일 수 있다는 장점이 있습니다.
하지만 Redis 로 재고가 관리되기때문에 DB와 Redis 간 데이터 동기화 정합성을 지켜야하게됩니다.
장애 복구 과정에서 Redis와 DB 불일치 가능성이 존재하게됩니다. 
현재 프로젝트에서는 Redis 재고를 관리하는비용보다  DB내에서 재고=를 처리하는것이 
Redis 저장소도입, 데이터 정합성 측면에서 더 적합하다고 판단했습니다. 
향후 트래픽이 증가하여 DB가 병목이 되는 상황이 발생한다면 Lua Script를 이용한 원자적 재고 차감과 Redis-DB 동기화 전략을 함께 도입하는 방향을 고려하고 있습니다.

### 4-1 회고 문제점
이번에 선착순 쿠폰 발급기능을 동기 방식에서 비동기 방식으로 개선하면서 단순히 RabbitMQ를 적용하는 것보다  **어떤 범위까지 비동기로 처리할 것인지 중요한 설계 문제**라는 점을 경험했습니다.
초기에는 **쿠폰 발급(INSERT)만 RabbitMQ를 이용해 비동기로 처리**하는 방식을 선택했습니다. 하지만 성능 테스트 결과 락 내부에서 여전히 쿠폰 재고 감소(UPDATE)가 수행되고 있었기 때문에 이전 비관적 락 기반의 동기 방식과 비교했을 때 처리량과 응답 시간이 크게 개선되지 않았습니다.
이후 락 유지 시간을 더욱 줄이기 위해 **쿠폰 재고 감소까지 비동기로 처리하는 구조**를 검토했습니다. 이 방식은 API 응답 속도와 처리량을 향상시킬 수 있었지만 HTTP 응답만으로는 최종 발급 결과를 사용자에게 전달할 수 없게 되어 **SSE를 이용한 비동기 이벤트 알림**이 추가로 필요했습니다.
또한 RabbitMQ의 Consumer Concurrency를 무조건 높인다고 처리량이 비례해서 증가하는 것은 아니라는 점도 확인했습니다. Consumer 수가 증가하면 동시에 락을 획득하려는 요청도 함께 증가하여 락 충돌과 대기 시간이 늘어날 수 있었으며 결국 시스템 성능은 Consumer 개수뿐만 아니라 **락 경합, DB 처리 속도 병목 구간을 함께 고려해야 한다**는 점을 알게 되었습니다.
**이번 프로젝트를 통해 특정 기술을 적용하는 것 자체보다 트레이드오프를 생각하며 현재 서비스의 요구사항과 운영 비용을 함께 고려하여 기술을 선택하는 과정이 중요하다는 점을 배울 수 있었습니다.**
